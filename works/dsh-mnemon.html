dsh-mnemon

给 Agent 一套能查、能改、能追溯的长期记忆，而不是把聊天记录一直往前塞。

  • 分类 Agent
  • 角色 设计 + 实现
  • 起于 2026-06
  • 状态 持续维护

背景与目标

Agent 的上下文是有限的。每次开一个新会话，之前定下的约定、踩过的坑、写过的判断，全都得重新讲一遍。把聊天记录一路往前堆，token 先撑不住，检索也只会越来越糊。

所以这个项目的目标不是「记得更多」，而是「记得准、查得到、改得动」。三条硬指标：

  • 单次召回压到几百 token 量级，而不是几万；
  • 任何一条记忆都能追到它是什么时候、因为什么写进去的；
  • 存量有上限，逼着自己做摘要，而不是把原文一股脑塞进去。

结论先放在这里：记忆要做薄。薄的意思是每条都短、都能被改写，而不是把整段对话冷冻起来。

我具体做了什么

  1. 拆成两个存储层，而不是一张「记忆表」档案层放结构化长文，index.json 做索引，每篇 front matter 里带 revision，改动可追溯；洞察层放一句话级别的结论，可以软删。查询先看洞察，命中不了再翻档案 —— 大多数问题在几十 token 内就解决了。
  2. 检索做成关键词 + 向量双通道，不引入向量数据库元数据和全文交给 SQLite，向量走 bge-m3 的 1024 维，落成旁挂文件；查询时两路各取候选再合并排序。几十 MB 的量级上纯余弦足够快，省掉一个常驻服务和一整套部署。检索脚本就一个 sem_search.py，拷走就能跑。
  3. 同步按水位 + 指纹做增量每个工作区记录上次同步的水位（时间 + 序号），只处理水位之后有改动的文件；文件指纹（大小 + 修改时间）没变就直接跳过。Windows 上把大目录用 junction 分到别的盘，扫描时按 junction 分流，不重复遍历同一份数据。
  4. 清洗单独做一条流程按 id 前缀筛出目标集合，逐条软删（保留记录，可回滚），再统一 gc 回收。系统提示词那种噪声在入库前就过滤掉，不让它占预算。

为什么是双通道

只用关键词，问「上次那个限流的参数」找不到；只用向量，问「哪篇写了 Pages 的构建上限」会飘。两路候选合并再排序，比任何单路都稳，代价只是多算一次。

关键取舍

维度选了原因
存储SQLite + 旁挂向量文件单机、无服务，备份就是拷目录
向量库不上，纯余弦暴力算数据量小，维护索引比算一次更贵
记忆粒度一句一条长文没法复用，短句才能拼装
删除软删 + gc判断做错了要能退回去
全库上限10MB主动约束，逼着压缩而不是堆原文

结果

  • 全库压在 10MB 以内，索引和数据一起拷走就能换机器；
  • 单次召回是若干条短句，不是整段对话；
  • 增量同步只碰有改动的文件，日常几分钟内跑完；
  • 水位和指纹都落盘，中断之后能接着走。

下一步

现在最缺的是评估：召回准不准，全靠我自己读一遍判断。想做一个小评估集（问题 + 期望命中的条目），每次改检索策略都跑一遍，把「感觉变好了」换成数字。另外想把语义检索接进 recall 的自动路由 —— 关键词无命中时自己降级，而不是我手动跑脚本。
