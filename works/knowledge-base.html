知识库

13 个分类、80+ 篇笔记：从教学方法论迁移到工程实践的一次整理。

  • 分类 笔记
  • 规模 13 分类 / 80+ 篇
  • 格式 Markdown
  • 状态 持续更新

背景与目标

教过英语课，教案、讲法、学生常错的地方，都在纸和聊天记录里；工程笔记散在收藏夹、临时文件和截图里。找的时候全凭记性，改过一遍的老结论也常常被自己重新踩一遍。

目标不是「多写」，是「写完之后能找到，并且知道它过没过期」。

我具体做了什么

  1. 先定分类，再写内容13 个分类封顶。分类超过十几个，就一定会出现「这条放哪都行」，然后就乱放。定死上限，新主题先塞进最接近的，等真长出第三篇再拆。
  2. 每篇都有 front matter标题、分类、更新时间、状态（草稿 / 可用 / 过期）。索引页从 front matter 生成，不手维护目录 —— 手维护的目录迟早和正文对不上。
  3. 一条迁移规则：一主题一篇，超 400 行就拆长文难维护也难复用。拆成一篇主文加若干细节篇，主文只留判断和入口。
  4. 全部 Markdown + 相对链接能 diff、能 grep、能进 git，离线也读得了。不用需要联网的笔记服务，也不用导出功能来换机器。

把教学结构搬到笔记上

讲课时有效的结构是：先给结论，再给一个反例，最后留一道能自己验的练习。写工程笔记时我照搬了这套 —— 结论在前，常见的错法单独一段，最后写「怎么确认你做对了」。比起按时间线记录，这套结构更耐读。

关键取舍

维度选了原因
格式Markdown可版本化、可离线、可迁移
分类13 个封顶逼着合并，而不是无限细分
目录front matter 生成索引可再生成，不会失效
链接相对路径换机器、换路径不断链

结果

  • 13 个分类、80+ 篇；
  • 索引页由脚本生成，改完 front matter 重跑即可；
  • 从教学沉淀下来的方法（拆步骤、给反例、留练习）直接套到工程笔记上；
  • 整套内容可以直接进版本库，改动能看 diff。

下一步

把「教学 → 工程」的映射表单独成篇：怎么把讲给别人听的结构，变成写给未来的自己的结构。这是我认为最值得写、也最容易被跳过的一篇。
