把 Agent 的记忆做薄，而不是做大

四个月里我把一个记忆库从 34MB 删到 9MB，召回反而变准了。这篇写给想给自己做个长期记忆的同行。

  • 发布 2026-11-21
  • 阅读 约 7 分钟
  • 标签 Agent · 记忆 · 检索

第一版：把记忆做成了垃圾桶

最初的实现很朴素：每轮对话结束，把这一轮的结论写进一个 JSON 文件，下次启动时取最近 N 条塞进上下文。前两周效果很好，第三个月开始明显变差——库里堆了四千多条，检索取前 5 条，其中三四条是「好的，我来处理」「需要我继续吗」这类没有信息量的句子。

问题不在模型，在检索。存进去的东西没有结构，读出来的东西就没有优先级。那段时间我一直在调提示词，实际上是在用提示词补存储设计的债。

拆成两层，各自回答不同的问题

后来按「一条信息有多大」把存储拆开，边界一下就清楚了：

层单位典型内容取回方式
档案层整篇文档，带 front matter（title / revision / sourcePaths）「这个项目怎么部署」「某个技能的完整步骤」按主题整块取回
洞察层一句一条，带 category / importance / tags「偏好 pnpm 而不是 npm」「这个仓库禁止裸 as any」向量 + 关键词

档案层回答「这件事的完整做法是什么」，洞察层回答「他知道什么、偏好什么」。混在一起存，就会出现用一整篇部署文档去回答一个偏好问题的情况——既浪费上下文，又答不准。

做薄的五条规则

体积不是靠定期清理解决的，是靠写入时就拒绝垃圾。我最后落成五条：

  • 一条只写一个事实。「他喜欢用 Python 做数据处理，讨厌写前端，Windows 上用 junction 管目录」——这是三条，写一行就废了。
  • 写之前先搜。命中相似内容就跳过，宁可缺，不要重。重复写入比不写更伤检索质量。
  • 软删 + gc。删除只打 deleted_at 标记，累积到阈值再物理清理。留出反悔窗口，也避免了频繁重写整个文件。
  • 容量上限当硬约束。全库 10MB 是天花板，不是建议值。写满就逼着自己排序：哪条真的有用？删的过程本身就是一次重要性评估。
  • 不存能重新算出来的东西。文件列表、目录树、git 状态这类，随时可以现查，存进去只会过期。
记忆的价值不在体积，在命中率。做薄不是妥协，是让每一条都有被取回的理由。

检索：先向量，再关键词兜底

嵌入用 bge-m3，1024 维；检索是纯余弦，没有 ANN 索引。有人会问是不是太慢——实测万条以内，一次 numpy 矩阵乘法 20 毫秒出头，上 HNSW 属于过早优化，还多一个要维护的结构。

关键词通道（SQL LIKE / FTS）必须保留。中文分词在专有名词上很不稳：查「水位」「指纹」「软删」这种词，向量会把语义相近但无关的内容捞上来，字面匹配反而准。两条通道取并集再按分数排，比单走向量稳。

排序时给 importance 一个乘数，但不过度加权。试过把 important=5 的权重放得很大，结果每次召回都是那几条「核心原则」，具体问题反而被挤掉。

增量同步：水位加指纹

多个工作区要汇进同一个库，全量重扫太慢，于是记两个东西：

  • 水位：上次同步到的最大 mtime / 序号，只处理更新的部分。
  • 指纹：文件 size + mtime + hash，三项都没变就跳过；只有 mtime 变了但内容没变（常见于 checkout、格式化）也跳过。

目录用 junction 挂进来的外部工作区单独分流，避免软链接环路把同步卡死——这是踩过的坑，不写这一条，第一次跑就会在某个循环链接上转到超时。

结果

  • 召回质量：从「5 条里 1 条有用」变成「5 条里 3 到 4 条有用」。
  • 上下文占用：同样任务下，记忆注入的平均 token 下降约 60%。
  • 全库体积：从 34MB 压到 9MB 以内，且不再随时间单调增长。

最有用的其实不是这些数字，是删东西这件事本身变得容易了。设计成能删，才敢往里写。
